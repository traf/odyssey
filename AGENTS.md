# Odyssey

Unofficial [Cosmos](https://cosmos.so) client. npm-workspace monorepo.

## Structure

```
apps/
  web/   Next.js 16 (App Router) — Cosmos API + web frontend. Deployed to Vercel.
  mac/   SwiftUI macOS app (Swift 6, SwiftPM executable). Consumes the web API over HTTP.
```

Root scripts (`dev`, `build`, `lint`, `start`) proxy to `apps/web`. One hoisted `node_modules`/lockfile at root.

## API

Lives in `apps/web`, not a separate app — it's serverless routes that deploy for free with the frontend. Only split out if it needs independent scaling/deploys or gains heavy auth/caching logic.

- Core logic: `apps/web/app/lib/cosmos.ts` (wraps the Cosmos GraphQL API), types in `lib/types.ts`.
- Public routes: `app/api/[username]/[[...cluster]]` and `app/api/search?q=` (README-documented + listed in the `Endpoints` modal, in-memory cached 5m via `cached()` in `lib/cache.ts`). They all return the same flat `{ images, count }` shape — keep it that way; the cursor/element detail belongs to the internal routes. `search` returns only the first page, since draining all 500 upstream matches would risk the function timeout.
- Internal routes used by the frontend + mac app: `app/api/cosmos/{resolve,elements,clusters,cluster-elements,search}` (CDN headers via `lib/cache.ts`: `s-maxage=15s` + `stale-while-revalidate=1d`).
- **Cosmos has no sorting.** No query takes an `order`/`sort` argument and neither do the `filters`/`meta` inputs (introspection is blocked upstream, so this was established by probing field names against validation errors). Any ordering beyond "recently added" is therefore local, over whatever is loaded — see `Sort.swift` in the mac app. Elements carry a `colors` palette (dominant swatch first, empty for older elements and for search hits, whose `ElementTile` type doesn't expose it) which is what the color sort orders by.
- `search?q=` is global element search across all of Cosmos (Cosmos' `searchElements`, 40/page, cursor-paginated). It's semantic — the upstream expands the query with related concepts and orders by relevance, so results must never be re-sorted by date, and a nonsense query still returns matches rather than nothing. Cosmos exposes no way to scope search to one user (its `userId` filter needs auth and returns empty), so search is always global.

The mac app mirrors these types in `apps/mac/Sources/Odyssey/Models.swift` and hits the routes via `API.swift`. If you change an API response shape, update both sides.

## Conventions

- **Web**: Tailwind only, no component libraries, minimal DOM. Reuse existing components (`Button`, `Card`, etc.). Watch for hydration issues.
- **Mac**: 1000% native — always use native Swift/SwiftUI components, never reinvent them. Lean hard into Liquid Glass (`.glassEffect`, `glassEffectID`, glass button styles, etc.) throughout the UI. SwiftUI + `@Observable`. `API.baseURL` defaults to the deployed URL; point at `http://localhost:3000` for local dev.
  - **Design tokens are the single source of truth.** All color, font, and spacing live in `Theme.swift` — never hardcode a raw color/size in a view. Change it once there.
  - **Componentize everything.** One-word-named, display-only components (`SearchField`, `Glass`, `Logo`, `Masonry`, `Lightbox`, `Splash`, `Sidebar`, `Gallery`). If an element could appear twice, make it a component with props. Logic/state lives in `GalleryModel`.
  - **Never load an original image.** `cdn.cosmos.so` renders on demand (`?format=webp&w=<px>`, same as the web `Card`), and originals average ~2 MP against tiles a few hundred points wide — it's decoded pixels, not bytes, that cost memory and heat. Ask for a rendition via `CosmosElement.image(width:)`, which snaps to 200px steps so zooming reuses cached renditions. The grid isn't lazy (a custom `Layout` realises every tile), so tiles also gate their fetch on `onScrollVisibilityChange` — measured in a harness: 13 of 300 children report visible, and the API works inside a custom `Layout`. Tiles keep their image once loaded, so scrolling back re-decodes nothing. Tile width comes from `onScrollGeometryChange`, never a `GeometryReader` — but treat that reading as a *hint about quality only*. Measured in a harness: inside a `NavigationSplitView` it sometimes fires once with a nonsense width (20pt for a 780pt pane) and never corrects, which zeroed the tile width and stopped every image loading. Implausible widths fall back to a normal column width, and the first `eagerTiles` load without waiting to be told they're visible, so no sizing or visibility signal can leave the grid blank.
  - **`MasonryLayout` caches its measurements** keyed on column width — a pass needs the same heights twice (size, then place), and SwiftUI runs passes per frame during resizes. Harness numbers over 20 frames: 7500 measurements resizing and 300 at a steady width, against ~12000 either way uncached.
  - **Zero layout shift, always.** Reserve exact space for async media — tiles size to their API `width`/`height` aspect ratio before images load. The masonry uses the native `Layout` protocol (`Masonry.swift`), never `GeometryReader`, so sidebar toggles and resizes animate smoothly with no reflow jump.
  - Motion uses one shared bouncy-but-fast spring, `Theme.spring` — reuse it for every interaction animation (never inline timings). Continuous spinners are the exception.
  - **Trackpad haptics on every discrete action** — zoom, cluster change, image open/close, modal open/close. Always fire through the `Haptic` helper, never call `NSHapticFeedbackManager` directly.
  - **Modals are the `Modal` component** — dimmed + 2px-blurred backdrop, click-outside or Esc to close, rounded to `Theme.corner`. Content-only views (e.g. `Account`) go inside it; the close control is the reusable `IconButton`.
  - **Keyboard shortcuts** — ⌘, settings, `/` search, ⌘S sidebar, ⌘Z Zen mode (hides all chrome, images only), ⌘+/⌘−/⌘0 zoom. Register in `OdysseyApp` commands, drive state via `GalleryModel`, and list them in the `Account` modal as `Shortcut` rows.
  - Bare-key shortcuts (no ⌘) can't be menu commands — AppKit matches menu key equivalents before the responder chain, so they'd swallow the character while typing. Use the `.keyShortcut(_:enabled:action:)` modifier in `Keyboard.swift`, which ignores keys while a field is being edited.
  - **The fade under the toolbar is ours, not the system's** — the `Fade` component overlays the top of the gallery (and a mirrored one the bottom, `Fade(edge:)`), and `TitlebarChrome` (`Titlebar.swift`) keeps `.toolbarBackgroundVisibility(.hidden)` so the two don't stack. macOS 26's own scroll edge effect was tried first and abandoned: its blur layer is present in every window state (verified in a harness) but only blurs whatever happens to be behind it, so in practice the fade appeared and vanished with the window state, and backdrop filters can't be captured in-process to debug it. `Fade` ramps the blur **radius**, not the opacity — a `CABackdropLayer` with a `variableBlur` `CAFilter` whose mask alpha *is* the radius, which is the same pair macOS uses for its scroll edge effects. Masking a fixed-radius material by opacity instead (the first attempt) leaves half-transparent blur over sharp content and reads as a milky wash. The mask also eases off `Theme.fadeInset` in from the sides: a blur that stopped dead at the sidebar divider clamped its sampling there and smeared a bright seam down it, and spanning the whole window instead put the strip over the sidebar and ghosted the search field. The mask is a plain bitmap, so its alpha can be read back and checked numerically — do that instead of eyeballing, since backdrop filters can't be screenshotted in-process. Don't sample the backdrop at half resolution or clip it with `masksToBounds`: both turn the inner edge of the strip into a 1–2pt seam even when the mask is already at zero. Leave a dead zone of clear mask at that inner edge so the radius dies inside the layer, not on its bound. Both classes are private, so `Fade` checks for them and falls back to a gradient-masked `.ultraThinMaterial`. Don't use `.windowStyle(.hiddenTitleBar)` or `titlebarAppearsTransparent` either — the title goes away with `.toolbar(removing: .title)`.
  - **`ToolbarItem(placement: .principal)` does not centre anything on macOS** — it drops into the title slot right after the sidebar section (measured: x=332 of a 1200pt window). Anything that must be centred, like the mark in the header, is an `.overlay(alignment: .top)` on the gallery, sized to `Theme.titlebar` and reaching up with `.ignoresSafeArea(edges: .top)`. That centres it on the detail pane — over the middle column. Content drawn there is visible but **not clickable**: verified by hit test, a click over the mark lands on `NSToolbarPrimaryTitleContainerView` and a SwiftUI button there never fires (and a second click zooms the window). To make it clickable, add `.titlebarClick { }` (`Titlebar.swift`), which parks a hit-catching `NSView` in the titlebar above the toolbar and keeps it on the SwiftUI view's frame. It claims only its own bounds, so the rest of the titlebar still drags the window, and if the titlebar hierarchy ever changes the catcher just isn't installed and the content goes inert. **Installing it once isn't enough** — hiding the toolbar (Zen mode) and showing it again rebuilds the titlebar, which left the catcher in a container that no longer exists and killed the click, so it re-checks its parent on every layout pass and re-adds itself if anything the restored toolbar brought lands on top of it.
  - **White chrome over unknown imagery carries its own shadow, not a blend mode.** The `Mark` uses two shadow passes (tight for the edge, wide to seat it). Mix-blend was tried and measured with `ImageRenderer` over greys from white to black: `.difference` reads brilliantly at both ends but falls to *zero* contrast wherever the image matches the inverted mark (mid-grey), and adding a halo only moves that dead spot — best worst-case 0.11. The two-pass shadow holds 0.49 at the mark's edge across the whole range and keeps the mark white rather than inverting to a colour.
  - **A toolbar dropdown is a `Button` that opens an `NSMenu`** (`SortPicker` + `SortMenuAnchor`), never a `Menu` or `Picker`. Measured in a harness: a toolbar `Menu` rebuilds its label as a title-and-icon pair and discards every layout modifier — the item stays 71pt wide at 0, 16 *and* 32pt of label padding — and `.menuStyle(.borderlessButton)` flattens it into an AppKit button cell, which drops the image entirely and draws any icon *before* the title. A `Button` keeps the label verbatim (82 → 114 → 146pt across those paddings), so the title, gap and padding are ours and the glass capsule matches the hit target exactly. Anchor the menu with an `.overlay` on the **button**, not inside its label: the overlay spans the 36pt capsule, while a label background is only the 16pt text box. Never pad or frame the control from outside — the toolbar draws glass over the padding without enlarging the hit target, so clicks near the edge fall through to the titlebar (doing nothing, and zooming the window on the second one).
  - **A matched-geometry group belongs to one zoom, not to one element.** The tile and the lightbox pair up on `Hero.id(element, zoom:)`, keyed on the zoom counter. Keyed on the element alone, reopening an image inside the previous dismissal's morph put three views in the group — the tile, the outgoing lightbox and the incoming one, all `isSource: true` — and the new lightbox resolved against the stale source and stayed at the tile's frame (measured: 375x254 in a 1200pt window), which reads as the popup opening empty. Both views must stay sources: as a follower the lightbox takes the tile's frame and never grows, since the tile stays in the hierarchy (hidden) the whole time. Reproduce timing bugs like this by driving `openZoom`/`dismissZoom` from a `.task` and logging the image's `onGeometryChange` size — hold ~300ms then reopen after ~80ms fails every time on the old key.
 - **A cancelled request is not an error.** The app cancels its own loads constantly — superseding a selection, calling off the background sort drain — and URLSession reports that as `URLError.cancelled`. Every `catch` filters it with `Error.isCancellation` (`API.swift`), and the gallery only shows an error state when `elements` is empty, so a late failure can't replace a grid that's already loaded.
 - **A silent refresh must not throw away loaded pages.** Focus restore re-fetches the first page so Cosmos edits show up; replacing `fetched` with that page deleted everything the user had scrolled in, the content shortened, and the scroll view sprang to the top (quit Slack, come back, grid runs away). `mergeFresh` no-ops when the first page is still the head of what's loaded, prepends newcomers, and only replaces when the feed is actually different.
  - **Never use a system `ProgressView`/spinner.** Every loading indicator is the spinning Cosmos mark — use the `Spinner` component (or the in-field spinning `CosmosMark`). The logo *is* the loader.
  - **Shipping / releases**: to ship a Mac update, follow this exact flow so the in-app update check works:
    0. Move the `## Unreleased` notes in `apps/mac/CHANGELOG.md` under a new `## <version>` heading, and use them as the GitHub release notes. Keep adding entries under `## Unreleased` as you make changes between releases.
    1. Pick the next **semver** version (`MAJOR.MINOR.PATCH`, e.g. `1.0.1` for fixes, `1.1.0` for features).
    2. Bump `Updater.fallbackVersion` in `Updater.swift` to the same `<version>` (dev builds have no Info.plist and use this as their version).
    3. `apps/mac/scripts/release.sh <version>` — builds, Developer-ID signs, notarizes, staples, and packages `dist/Odyssey.dmg` (that `<version>` is written into the app's `CFBundleShortVersionString`). Creds in `apps/mac/.env.release` (gitignored).
    4. Create a GitHub release tagged **`v<version>`** (the `v` prefix matters — `Updater.swift` strips it) and upload `Odyssey.dmg` as an asset named exactly `Odyssey.dmg`. Publish it as the latest release. The DMG installer window is built the way [Native](https://github.com/vercel-labs/native) does it (`scripts/dmg.sh`): writable HFS+ image, Finder AppleScript for background / icon size / positions, then UDZO. The art (`scripts/background.swift`) is `apps/web/public/dmg.jpg` plus a light arrow, shipped as a 1×/@2× TIFF — Finder draws the names itself. Don't hand-write a `.DS_Store` with a `pBBk` bookmark; macOS 26+ discards those.
    5. Keep the release notes body leading with the direct download link (`releases/latest/download/Odyssey.dmg`).
    - The app has **no auto-updater**. On launch `Updater.swift` fetches the latest release tag from the GitHub API and, if it's newer than the running `CFBundleShortVersionString`, shows an "Update available" button in the `Account` modal that opens the releases page for a manual re-download. The web "Download for Mac" button links to `releases/latest`.
    - To re-cut the *same* version (e.g. a fix before anyone downloaded): rebuild with the same `<version>`, delete the old release asset, and re-upload — keep the tag `v<version>`.
  - Public data only (no auth) — all data comes through the Odyssey web API.
- Don't start dev servers — one is usually running.
